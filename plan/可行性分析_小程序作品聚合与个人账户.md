# 可行性分析：小程序作品聚合 + 个人账户上移动端

> 分析日期：2026-11-05（同日修正）
> 分析对象：「把所有作品的移动端聚合进一个微信小程序，由小程序点进对应模块」，重点先做「个人账户」
> 现状前提：小程序「悦读且住」**已发布上线**（备案 `陇ICP备2026009894号-1X`，2026-10-15 通过；AppID `wx216042d45300a3f9`，已按 mp 后台截图核对）
> **修正说明**：初稿按「尚未提审 / 尚未发布」判断，用户于 2026-11-05 确认已上线，相关结论已同步修正（不影响主结论）。

## 一句话结论

**别做「一个大聚合壳」，做「一个作品一个入口 + 统一账户（uid）在后台串起来」；「个人账户」这条先做——而且它已经接好 80% 了，只是被藏在「设置」页里。**

技术上，个人主体小程序有四道硬门槛（不能 `web-view`、不能拉 `URL Scheme`、不能跳个人主体小程序、大概率不能关联公众号），这四道合起来就把「一个壳装下所有作品」堵死了。产品上，你目前的真实用户量还很小（官网累计 13 UV；小程序虽已上线，真实用户量待看 mp 后台），现在为想象中的流量做重架构不划算。

## 一、有没有真实用户

| 证据 | 数值 | 来源 |
|---|---|---|
| 官网访问统计 | 累计 **13** UV，今日 **5** | `https://chesterlee.cn/stats/summary`，2026-11-05 实测 |
| 统一账户中心 | 服务在线（`/healthz` → `ok`） | 2026-11-05 实测 |
| 小程序「悦读且住」 | **已发布上线**；真实访问/用户数看 mp 后台「数据 → 概况」 | 用户 2026-11-05 于 mp 后台确认（AppID `wx216042d45300a3f9`） |
| 小程序大盘 | 微信小程序 MAU 约 **9.62 亿**（2026-06） | QuestMobile 小程序报告 |
| 微信读书 DAU | 约 **340 万** | QuestMobile 夜经济报告（口径：日活） |

**结论：**

1. 「小程序流量大」是**平台事实**，不等于「你的小程序有流量」。小程序已上线，但真实用户量只有 mp 后台能看到——**下一次决策前先看一眼「数据 → 概况」的访问人数 / 新访问用户**，别拿平台大盘当自己的成绩。
2. 所以决策标准应该是：**自己用着顺手、以后能扩**，而不是「为 9.6 亿用户设计一个聚合平台」。
3. 与竞品的真差异：微信读书自己做「阅读 + 社交」，你做的是「一个人的作品集合 + 一个账号走遍」——**对陌生用户没有吸引力，对你自己和熟人有用**。别把它包装成平台。

## 二、可行路径对比

| # | 路径 | 能实现吗 | 门槛 | 用户要不要装新东西 | 主要风险 |
|---|---|---|---|---|---|
| **A** | 一个大聚合壳（主小程序 + 内嵌/跳转其它作品） | ❌ 个人主体走不通 | 需企业主体 + `web-view` + 各作品单独成小程序 | 只需装一个小程序（体验最好） | 个人主体四道红线全撞上；做成「导航/平台」有审核驳回风险 |
| **B** | 一个作品一个小程序，账户在后台串联 | ⚠️ 可以做，但重 | 每个作品都要单独注册 + 备案（个人主体最多 5 个） | 要装 N 个小程序 | 备案 ×N、维护 ×N、用户跳转需主动点击 |
| **C** | 小程序只做「账户 + 作品清单（纯文字 + 复制链接）」 | ✅ 能做 | 无额外资质 | 装 1 个 | 体验弱：点进去还是浏览器 |
| **D** | **小程序只做微信悦读，把「账户」升级成独立 tab（推荐）** | ✅ 现在就能做 | 无 | 装 1 个 | 最小，几乎无风险 |
| **E** | H5 聚合页（`chesterlee.cn/works.html` 加登录态），小程序不聚合 | ✅ 能做 | 无 | 不用装 | 拿不到微信流量 |

**路径差异的实话：**

- A 与 B 的差别其实是「谁承担跳转成本」。A 体验好但个人主体根本做不到；B 做得到但用户要装 5 个 App 级的东西。
- C 与 D 的差别**很小**——都是在「我的」里多一张作品清单。C 多一个「复制链接」，D 少一点。别为这点差别纠结。
- **真正有价值的只有一件事：把 uid 打通。** 打通之后，用户在哪个入口都能找回自己的数据，这跟「聚不聚合」无关。

## 四、隐藏坑

1. **AppID 已对齐**：mp 后台截图、`通用信息/账号/微信公众平台.md`、`mobile/project.config.json` 三处现在都是 `wx216042d45300a3f9`（2026-11-05 核对）。此前流传的 `wx216042d45300f9` 是错记，已作废。
2. **「个人账户」不是没启程，是已经做完了**。`settings` 页第一张卡「登录与同步」已经支持「微信一键登录」和「6 位码绑定」，登录后显示昵称头像 + 「进入账户中心」。用户感知不到，是因为它只是一张卡，不是一个入口。
3. **已发布，但每次改版都要重新提审**（1~7 天）。类目一旦选错被打回，会浪费一次提审机会；大改版前先确认类目仍是「工具 → 效率」。
4. **账户码永远只回掩码**（`me` 接口规则）。小程序端不能设计「显示完整账户码」，否则违反接入契约。
5. **跨端绑定只能靠 6 位码**。小程序内既不能收短信、也不能 `getPhoneNumber`，「网页端生成码 → 小程序输入」是唯一的路，页面上必须写清楚引导，否则用户会卡住。
6. **隐私指引必须和实际采集一致**：昵称头像 / 相册（仅写入）/ 摄像头 / openid 云同步，四项已登记；如果新增作品列表上报（`track`），要补一条说明。
7. **账户中心是单进程 Node + JSON 存储**。现在这个量级完全够；但别在小程序里做高频轮询。
8. **微信读书数据依赖官方网关**。网关一变，小程序就空。这是既有风险，不是本次新增的。
9. **个人主体不能微信认证** → 没有认证标识、搜索权重低、`wx-open-launch-weapp` 等能力永久缺失。这是「要不要升级主体」的核心决策点。

## 五、推荐方向 + 最小验证清单

### 5.1 主线（推荐）：路径 D —— 把「我的」tab 升级成「账户」tab

不新建项目、不加页面栈，只做三件事：

1. **「我的」tab 改名为「账户」**，顶部就是「我是谁」（头像 / 昵称 / uid / 一键登录 / 6 位码绑定）。复用现有 `shared/psauth.js`，零新依赖。
2. **第二段「我的作品」**：调 `me.products`，列出已登记作品卡，点一张 → 复制链接 + 提示「用浏览器打开」（个人主体只能这样）。
3. **第三段「账户安全」**：绑定引导（去 `account.chesterlee.cn` 生成 6 位码）、注销账户入口（`account.delete`）、隐私政策 / 用户协议。

**为什么是这条**：成本最小、零资质风险、复用 80% 已完成的东西；而且「账户」这个入口一旦立起来，以后加什么作品都只是往列表里加一行。

### 5.2 备选：路径 C —— 账户 tab + 弱聚合作品清单

和主线几乎一样，差别只是把「作品清单」做成更显眼的一屏。**如果主线做完觉得够用，就不需要这个「备选」。**

### 5.3 兜底：路径 E —— 把 H5 聚合页做好，小程序不聚合

`chesterlee.cn/works.html` 加登录态，做成「我的作品 + 我的账户」的网页版。手机浏览器能开，微信里也能开（H5 不受个人主体限制）。

### 5.4 明确不推荐：路径 A（大聚合壳）

四道硬门槛撞三条，剩下一条（跳转小程序）还要每个作品单独注册备案。投入产出完全不成立。

### 合规红线

- 小程序**不能改名**：改名即备案失效（`陇ICP备2026009894号-1X` 绑定的是「悦读且住」）。
- 小程序**不用自己挂备案号**，发布后微信自动在「更多资料」展示。
- 账户页必须提供**注销**入口（已有 `account.delete`）。
- 不要把微信读书正文 / 书评**转存到你自己的服务器**再分发，版权风险在你这边。
- `track` 上报要实名到隐私政策里，且只上报「打开/使用」，不做行为画像。
