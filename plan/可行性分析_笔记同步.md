## 0. 一句话结论

**可行，且是"顺手就能做"的下一步**：数据侧（划线 / 想法 / 书籍元信息）我们**已经全部拿到**，缺的只是"把已有导出结果，稳定地写进笔记软件"这一层。
推荐**双通道**：**默认「下载 Markdown」零配置兜底**（马上能用）＋ **进阶「Obsidian Local REST API 直写」**（一键增量、无需手动搬运）。不建议一上来就堆多平台（Notion / flomo / Readwise），先只做 **Obsidian**，其余留接口。

> ✅ **已拍板（2026-10-16）**：只做 Obsidian；先做「下载 Markdown」MVP；内容含划线、想法、AI 摘要/复习卡、书评/热门划线、阅读人格。详见 §8。

## 1. 需求拆解

| 项 | 内容 |
|---|---|
| **用户目标** | 微信读书里的划线 / 想法 / （可选）书评，自动落进个人知识库（Obsidian），和已有笔记形成知识网络，而不是散在 App 里 |
| **输入** | 现有笔记模块已抓到的 `highlights`（划线）＋ `thoughts`（想法/批注）＋ 书籍元信息（书名/作者/封面…） |
| **输出** | 每本书一个 `.md` 文件，按章节分组的 Markdown；写入 Obsidian vault（直写或下载后导入） |
| **成功标准** | ① 一键（或一次点击批量）完成同步；② 结构稳定、可反复同步不产生重复/错乱；③ 用户手写的笔记不被覆盖；④ 全程本地、不外传数据 |

## 3. 目标侧调研：生态里别人怎么做

### 3.1 微信读书自身的笔记模块（App / 网页）

- **书籍内笔记页**：单本书「读书笔记」可按划线 / 想法 / 书签分类查看；App **7.3.5+** 提供"导出 → 复制到剪贴板"。
- **个人中心跨书笔记**：可批量全选复制，但**是纯文本、无结构、无时间戳**；网页版多靠 Ctrl+A 复制，格式极易丢失。
- **书签不给内容**：官方只给数量（`reviewCount + noteCount + bookmarkCount`）。
- **官方 Skill（2026-05 发布）**：开放 API Key（`wrk-` 开头），能力含**笔记/划线导出、热门划线、书评、书架、阅读统计**——这正是我们扩展已经在用的那套网关。
- **共性问题**：微信读书**没有**"同步到本地知识库"的官方通道，全靠第三方补这一步。

### 3.2 生态里已有的三类做法

| 类别 | 代表 | 机制 | 优点 | 短板 |
|---|---|---|---|---|
| **Obsidian 插件** | `obsidian-weread-plugin`（zhaohongxuan，18 万+ 下载） | 插件内直连微信读书 **API Key / Cookie 双认证**，**覆盖式**同步为 `.md`；block id `^bookmarkId`；模板系统、Daily Notes、热门划线 | 成熟、模板可定制、被大量验证 | 需在 Obsidian 侧装插件、Cookie 会话会失效需维护；**它独占**了"同步"这件事，但不会用我们扩展的能力 |
| **浏览器扩展** | 微信读书笔记同步助手（Chrome）、WeRead Export、Notepal | 在阅读页抓数据 → 直接写 **Notion API** 或 **Obsidian Local REST API**；Notepal 覆盖 Readwise/Notion/flomo/思源 | 就在浏览器里、一次点击 | 多数只做"导出/一次性"，增量与冲突处理较弱；多平台适配成本高 |
| **本地脚本** | `wereader`（Python GUI/CLI，扫码 Cookie） | 扫码缓存 Cookie → 拉数据 → 存 `notes/*.md` | 可编程、可批量 | 需本地跑 Python、要维护 Cookie、脱离阅读场景 |

### 3.3 关键结论（给我们用）

1. **"微信读书 → Obsidian"已被验证可行**，主流做法就是**覆盖式同步 + 稳定 ID + frontmatter 标记**，我们照抄这套数据模型即可，无需自创。
2. **我们能做的差异化**：扩展**已经在阅读页、已经拿到数据、已经有 AI（DeepSeek）与复习/朗读能力**——可以把"同步"做成"同步 + 复习卡 / 摘要 / 按书检索"，而不是单纯搬文件。
3. **写盘通道就三条**，见下节。

## 4. 可行性判断

| 维度 | 判断 | 说明 |
|---|---|---|
| **技术** | ✅ 高 | 数据已通；写盘有三条成熟通道（下载 / Local REST API / 平台 API）；`manifest.json` 已有 `optional_host_permissions: ["https://*/*"]`，可**运行时**申请 `http://127.0.0.1/*`，不必安装即弹权限 |
| **合规 / 红线** | ✅ 可控 | 全程本地、走用户自己的 Key；**不新增默认权限**；只需在 `release/privacy.md` 与商店文案同步说明"可写入本地笔记软件" |
| **成本** | ✅ 低（MVP） | MVP 只做"下载 Markdown"，几乎零新增依赖；直写 Obsidian 需新增一个后台通道 + 一份文件规格 |
| **多端一致性** | ✅ 明确 | 按既有决议：（H5 / 小程序）**不做**——本地写盘依赖桌面浏览器；**只在扩展端做**，不破坏双端镜像原则 |
| **竞争** | ⚠️ 有 | `obsidian-weread-plugin` 已很成熟；我们的价值在"**不用另装插件**、且与扩展的 AI / 复习 / 定位原文打通"，文案上**不贬低、只讲差异化** |

## 5. 建设思路（推荐架构）

### 5.1 总原则（照抄成熟做法，避免踩坑）

1. **覆盖式同步**：每次同步基于官方最新数据**重渲染并覆盖**，**只覆盖"我自己生成的文件"**；用户手写笔记一律不碰。
2. **稳定 ID**：划线用 `bookmarkId`、想法用 `reviewId` 作锚点 → 生成 block id `^wr-bk-<id>` / `^wr-rv-<id>`，供用户用 **Obsidian 块引用**在外文件批注（这是官方推荐的"永久笔记"打法）。
3. **frontmatter 标记**：文件头写 `type: weread-highlights`、`book: xxx`、`wereadId: xxx`、`syncedAt`、`source`，既便于 Dataview 检索，也让同步器能识别"哪些文件是我生成的"。
4. **全程本地**：数据不出本机；不引入远程服务。

### 5.2 三条落地通道（按推荐度）

| 通道 | 机制 | 配置门槛 | 适用 |
|---|---|---|---|
| **A. 下载 Markdown**（默认兜底） | 复用现有 `downloadFile()`，导出 `书名.md` | 零 | 所有人。技巧：**把浏览器下载目录设为 vault 的子目录**，下载即入库，一键完成 |
| **B. Obsidian Local REST API 直写**（进阶） | 用户装 `obsidian-local-rest-api` 插件 → 开 **HTTP(Insecure) 端口 27123** → 复制 API Key；扩展后台 `PUT /vault/<路径>` 写文件、`PATCH` 更新指定 heading/block/frontmatter | 中（装插件 + 开端口 + 填 Key，一次性） | 想要"点一下、库里就更新"的重度用户 |
| **C. 云笔记平台**（储备，先不做） | Notion / flomo / Readwise 各自 API 或 webhook | 高（逐平台适配 + 平台侧门槛） | 后续按需，本方案**预留接口不实现** |

> 通道 B 的注意点（已核实）：HTTPS 端口 27124 用**自签证书**，浏览器默认会拦 → 优先引导用户开 **HTTP 27123**；该插件返回 `Access-Control-Allow-Origin: *` 且**不支持 `credentials: include`** → 请求走**后台 service worker**（带 `host_permissions`），不带 cookie 即可。

### 5.3 笔记文件规格（建议，可后续细化成模板）

```
WereadNotes/
├── 书摘/
│   └── 《置身事内》.md
└── _索引.md            ← 可选：按年份/分类的书目索引（P1）
```

单本书文件结构：

```markdown
---
type: weread-highlights
title: 《置身事内》
author: 兰小欢
wereadId: 33000xxxx
syncedAt: 2026-10-16 10:00
source: 微信读书官方网关
tags: [读书笔记/微信读书]
---

# 《置身事内》读书笔记

## 第一章 地方政府的权力与事务

> 这条是划线原文 ^wr-bk-9f3a2c

💭 这条是自己的想法（对应原文：…） ^wr-rv-7d1b0e
<small>2026-09-01 21:03</small>
```

要点：**章节 H2**、**划线用引用块**、**想法紧跟其配对的划线（用 `range` 配对，配不上的单列）**、**每条带稳定 block id**、时间戳保留。

### 5.4 复用关系（不改旧代码）

- **数据与导出**：复用 `modules/notes.js` 的取数、归一化、现有 Markdown 渲染（抽成共用 `buildNoteModel()`，面板导出与同步落地**共用一份模型**，避免两套渲染漂移）。
- **后台通道**：仿 `background.js` 里 DeepSeek / 官方网关的写法，新增 `wre-obsidian-ping` / `wre-obsidian-write` 消息 + 一个 `http://127.0.0.1:27123/*` 的**可选**主机权限申请。
- **界面**：在「📝 笔记」面板加「🔗 同步到笔记软件」入口（设置区填 API Key / 目标目录模板），**新功能写新模块**（如 `modules/sync-notes.js`），不动 `notes.js` 既有逻辑。

### 5.5 增量与冲突策略（避免"越同步越乱"）

- **覆盖式 + 按书整篇重写**：同一本书永远只对应一个文件，重同步=重渲染，天然不重复。
- **不做双向合并**：用户在同步文件里手改会被覆盖 → 文件头显式提示"此文件由微信悦读生成，请勿直接编辑；批注请用块引用写到别处"。
- **失败可续**：批量同步带进度与"停止"，单本失败不阻塞其它书；结果写进统一日志（沿用现有 `log()`）。

## 5.6 内容可达性（哪些能同步、哪些不能）

**关键限制**：同步**只在扩展端**做，而部分内容的生产端在 H5 / 小程序，扩展端**取不到**：

| 内容 | 生产端 | 扩展端能否同步 |
|---|---|---|
| 划线 / 想法 / 批注 | 微信读书官方接口 | ✅ 可以（现成） |
| 书评（`/review/list`） | 微信读书官方接口 | ✅ 可以（需先接接口，现为 P1 储备） |
| 热门划线（`/book/bestbookmarks`） | 微信读书官方接口 | ✅ 可以（需先接接口，现为 P1 储备） |
| AI 摘要 / 复习卡 | 扩展内 DeepSeek | ✅ 可以 |
| 阅读人格（读书人版） | 扩展 `official.js`（阶段十四） | ✅ 可以 |
| **灵感漫游** | **H5 / 小程序**（本地 localStorage / 云端） | ❌ **扩展端取不到** |
| **每日卡片** | **H5 / 小程序** | ❌ **扩展端取不到** |

**结论**：本轮（扩展端）落地 ✅ 的 5 类。**灵感漫游 / 每日卡片**若要入库，需**另在 H5 端**做同规格的「导出 Markdown」（与扩展共用同一套文件规格，H5 是网页、同样能触发下载），单列 P1、另行评估——不建议为此破坏"同步只在扩展端"的边界。

## 6. 分阶段实施建议

| 阶段 | 内容 | 说明 |
|---|---|---|
| **MVP（先跑通）** | 扩展「📝 笔记」→「⬇️ 导出 Markdown（按书分文件）」：**划线 + 想法** → 文件规格 v1（frontmatter + 章节 H2 + 划线引用块 + 想法配对 + 稳定 block id） | 复用现有取数 / `buildMarkdown` / `downloadFile`；用户把**浏览器下载目录指向 vault 子目录**即完成"同步"，零配置 |

| **V3（真同步）** | Obsidian Local REST API 直写 + 连通性检测 + 目录/模板设置 | 用户装 `obsidian-local-rest-api` 并开 HTTP 27123 后，点一下库内即更新 |
| **P1（另议）** | 灵感漫游 / 每日卡片 → 需在 **H5 端**做同规格导出（扩展端不可达，见 §5.6）；Notion / flomo / Readwise 适配 | 按需求再评估 |

## 7. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| Local REST API 自签证书被浏览器拦截 | 直写失败 | 默认引导用 **HTTP 27123**；引导文案写清"装插件→开 HTTP 端口→复制 Key" |
| 新增主机权限触发商店/更新提示 | 用户疑虑 | 走 `optional_host_permissions` **运行时申请**；只在用户开启"同步"时才请求；`privacy.md` / 商店文案同步更新 |
| 官方接口/字段变更 | 同步内容缺失 | 复用现有"三级兜底 + 来源标注"；同步文件保留 `source` 字段，缺数据时显式提示"本次不完整" |
| 用户直接在同步文件里编辑 → 被覆盖 | 数据丢失焦虑 | frontmatter 标记 + 文件头警告 + 推荐块引用；同步前可选"先备份旧文件到 `.weread-backup/`" |
| 与 `obsidian-weread-plugin` 功能重叠 | 用户不知选谁 | 文案强调差异：**免装插件、与扩展 AI/复习/定位原文一体、可批量整库同步** |
| 多端一致性被破坏 | 违反项目红线 | 同步**仅在扩展端**实现；H5 / 小程序不做（已在 RPD 立项决议） |

## 8. 已确认决策（2026-10-16，用户拍板）

1. **目标平台**：**只做 Obsidian**；Notion / flomo / Readwise 仅预留接口，不实现。
2. **写盘方式**：**先做「下载 Markdown」MVP**；「Local REST API 直写」列为 V3。
3. **内容范围**：划线、想法 / 批注、AI 摘要 / 复习卡、书评 / 热门划线、阅读人格（读书人版）；
   **灵感漫游 / 每日卡片**因数据在 H5 / 小程序端、扩展端取不到，单列 P1 另议（见 §5.6）。
4. **数据一律本地**：走用户自己的 Key，不外传、不上传。

**写 RPD 时再细化**（暂不影响可行性）：文件 / 目录命名与模板、默认导出目录、同名文件是否覆盖、批量范围（当前书 / 全库）、书评与热门划线接入的展示口径。
