## 一句话结论

**需求是真的，方向也对；但"结合微信读书"有一条硬边界必须先讲清：微信读书官方能力是「只读」的——只能把它的数据读过来，不能把纸质书塞回去。**

所以你能做成的闭环是：

> **你自己的纸书库（能扫、能拍、能存、能写）+ 微信读书的电子书数据（有没有电子版、你的划线/想法/书评/推荐/进度）→ 两边互相索引。**

做不到的是：把纸质书"加进微信读书书架"，或让微信读书同步你在纸书上写的笔记。

**形态建议**：把「纸书」这一页**加进你已有的「微信悦读」小程序**（[wereadProxy](file:///Users/Admin/Knowledge/Coding/微信读书插件/mobile/cloudfunctions/wereadProxy/index.js) 云函数、共享模块、网关中转全是现成的），而不是新起一个孤立 App。

## 一、有没有真实用户——有，而且被验证了 9 年

- **晒书房**（2012–2021）就是干这个的：手机扫书背条码 → 自动建档 → 按馆藏分类。App Store 4.9 分、12284 个评分，被爱范儿/少数派等推荐。
- **它 2021-07-23 官方宣布停止服务**，理由"遇到一些难以克服的困难"（此前官网还有一则"应有关部门要求内容整改"的通告）。这告诉你两件事：① 需求真实且用户量大；② **这个品类本身极难养活自己**——做了 9 年、免费，还是死了。
- 它死后空档是真被用户惦记的：豆瓣小组有人在求"还有和晒书房类似的 App 吗"，被推荐 私家书藏 / 藏书馆 / 二酉 / 云管书。
- （注：2026 年有些下载站又挂着"晒书房 v3.23.x"，但下载站日期多半是自动改的，**是否复活待核实**，别当事实。）

**你和它们反着来的点**——经得起推敲，但要诚实评估：

| | 晒书房 / 私家书藏 这类 | 你的设想 |
|---|---|---|
| 录入 | 扫 ISBN 条码 | 一样，但顺手查微信读书有没有电子版 |
| 之后 | 死档案（分类 / 标签 / 已读） | **关联**微信读书：电子版链接、你的划线/想法、书评、相似推荐、进度 |
| 跳转 | 无 | 一键跳微信读书电子版继续读 |
| 数据 | 单向录入 | **双向索引**：这本我有纸书 ↔ 这本我有电子版 |

**一句实话**：这个差异是真的，但它属于"锦上添花"——用户不会因为缺它就不用，只会因为有它更愿意用。**加分，不救命。**

## 二、两条硬边界（最大预期落差，先说清）

**边界 1：微信读书官方 Skill 只能读，不能写。**
官方口径：「目前仅支持读取个人阅读数据，**暂不支持自动加书架、同步笔记回传等写入操作，数据单向安全调用**」。

| 你想要的 | 能否做到 | 说明 |
|---|---|---|
| 纸书 → 加进微信读书书架 | ❌ | 网关只读；微信读书也没有"纸质书入库"这个概念 |
| 纸书笔记 → 回传微信读书 | ❌ | 写操作不存在 |
| 微信读书划线/想法 → 挂到你的纸书条目下 | ✅ | `/book/bookmarklist`、`/review/list/mine` |
| 纸书 ↔ 电子版一键跳转 | ✅ | 书名走 `/store/search` 找 bookId → 拼链接 |
| 用书名查有没有电子版 | ✅ | `/store/search` |
| 用 **ISBN** 直接查微信读书 | ⚠️ **待实测** | `/store/search` 的 keyword 吃不吃 ISBN，要实测 |

**边界 2："你买纸书的书，多半微信读书没有电子版。"**
很多人恰恰因为没电子版才买纸书。所以"关联"的覆盖率可能只有一部分，**这直接决定闭环感强弱** → 必须实测（见第五节）。

## 五、隐藏坑

1. **覆盖率未知**：纸书 ≠ 微信读书有电子版。这是最大的预期落差，必须实测。
2. **ISBN 元数据是隐形成本项**：免费的不好用、好用的要钱，豆瓣这条老路已死。要么买商业接口，要么用"微信读书书名反查 + 手动补"兜底。
3. **低频 + 难变现**：晒书房 9 年免费仍停服；个人主体小程序**不能收微信支付**，只能靠广告（且个人能否开流量主，网上口径互相矛盾，**待核实**，别把它算进收入）。
4. **版权红线（必须写进定位）**：**绝不能**做成"拍照把纸书 OCR 成电子书文库"——那是盗版分发。本项目只做"建档（元数据）+ 关联"，**不复制书中正文**。
5. **接口会变**：官方 skill 回包带 `upgrade_info` 时强制升级；接口清单以 `{"api_name":"/_list"}` 实测为准。

## 一、这套项目的"分类规矩"（现有约定）

看代码就发现它有一个稳定套路，我一直在沿用：

| 目录 | 规矩 | 例子 |
|---|---|---|
| `pages/<功能>/` | **一个功能 = 一个页**（4 件套 js/wxml/wxss/json） | `pages/shelf/`、`pages/notes/` |
| `shared/<功能>-<职责>.js` | **一个功能按"职责"拆成多个小文件** | `daily-core / daily-data / daily-store / daily-ai / daily-share` |
| `components/` | 跨页复用的 UI 零件 | `wre-state`（加载/空/错误/无Key 四态） |
| `cloudfunctions/wereadProxy` | 唯一出口，所有联网都走它 | 按 `action` 分流 |

关键的一条：**文件名后缀就是"分类标签"**，一眼能看出这文件是干嘛的：

- `-core` = 纯逻辑/编排
- `-data` = 取数（网络）
- `-store` = 本机存储
- `-ai` = AI 相关
- `-share` = 分享/导出
