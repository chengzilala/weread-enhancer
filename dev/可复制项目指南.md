> **提炼自**：微信悦读（weread-enhancer），已跑通「需求→开发→测试→版本→上架→交接」完整闭环

## 1. 适用范围与核心理念

**适用**：单人或「人 + AI」协作、面向零基础用户、原生 HTML/CSS/JS 的浏览器扩展或轻量前端。其余小型项目也大体通用（把「上架」换成对应「交付/部署」即可）。

**核心理念（照抄本项目已验证的原则）**：
- **目标优先**：先做出可用结果，再迭代变好看/更完善。
- **安全优先**：不输出、不落盘任何密钥/token/隐私。
- **旧代码不改，新功能写新模块**：降低回归风险。
- **文档随稳定版更新**：每到「能用且稳定」的节点，就更新 README / Running / version_plan。
- **避免过度设计**：优先「最短路径」实现，复用现有技术栈。

## 2. 标准目录结构（可复制骨架）

```
{{项目名}}/                    ← 项目根 = git 仓库根 = 代码窗口的工作区根
│
├── .trae/                     # 🤖 AI 协作配置（每个项目自带一份，Trae 不继承父目录）
│   ├── rules/
│   │   ├── general_rules.md        # 通用规则：角色/总原则/启动流程/红线（从母本复制）
│   │   └── project_rules.md        # 项目规则：定位/技术栈/作用域/命名/本项目红线（新写）
│   └── skills/                     # 5 个 skill，每个一个目录 + SKILL.md（从母本整目录复制）
│       ├── gen-rpd/  ├── pack-publish/  ├── session-handoff/
│       └── session-log/  └── test-checklist/
│
├── manifest.json            # 扩展入口（扩展类项目）
├── {{入口代码}}             # 如 content.js —— 核心逻辑
├── {{样式}}                 # 如 content.css
├── README.md                # 项目首页：介绍/安装/使用（顶部放介绍与用法）
├── .gitignore
│
├── plan/                    # 📋 规划：需求与版本
│   ├── RPD_需求文档.md          # 产品需求（唯一需求源）
│   ├── version_plan.md          # 版本历程 + 未来规划 + 时间线
│   ├── plan_github_versioning.md# Git 流程 + tag 归档表
│   ├── plan_{{store}}_store.md   # 每个商店一份上架/归档文档
│   └── session_handoff_*.md      # 会话交接（可直接粘给新会话）
│
├── dev/                     # 🔧 开发：规则与日志
│   ├── project-rules-v*.md      # 规则契约的历史版本快照（活跃规则在 .trae/rules/）
│   ├── 可复制项目指南.md         # 本文件
│   └── session_log.md           # 会话记录（固定 6 段摘要）
│
├── test/                    # 🧪 测试：每个功能一份验收清单（勾选项）
├── release/                 # 🚀 上线：privacy.md + 打包 zip（zip 不入库）
├── usage/                   # 📖 使用：Running.md（安装启动）+ 操作手册
├── icons/                   # 图标 16/48/128（扩展类）
├── screenshots/             # 截图：效果参考图（原图）+ promo（README 卡片）+ store（商店尺寸）
└── inbox/                   # 📥 临时待归类
```

> 目录职责单一、命名带前缀（如 CSS 类名统一 `wre-` 防污染）。新增维度先进 `inbox/`，稳定后再归位。

### 2.1 每项「装什么 / 新项目怎么来」

| 路径 | 装什么 | 新项目怎么办 |
|---|---|---|
| `.trae/rules/general_rules.md` | 通用规则（角色/总原则/启动流程/红线） | **复制**，只改开头说明块（生效范围、母本路径） |
| `.trae/rules/project_rules.md` | 项目规则（定位/技术栈/作用域/命名前缀/本项目红线） | **新写**（照 §6 占位符填） |
| `.trae/skills/` | 5 个 skill | **整目录复制**（母本：`AI协作规划库/2-技能_Skills/`） |
| `plan/` `test/` `usage/` `release/` `icons/` `screenshots/` `inbox/` | 见上方注释 | **建空目录**，从第一个文档自然长出 |
| `dev/可复制项目指南.md` | 本工作法（SOP + 模板） | **复制**（它就是给新项目用的模板） |
| `dev/session_log.md` | 会话记录 | **新建空白**（别复制别的项目历史） |
| `dev/log.md`、`*-debug-*.md` | 本项目专属调试记录 | **不复制** |
| `release/*.zip` | 上架包 | **不复制**（不入库） |

### 2.2 规则与技能的分发（三层，只从上往下改）

```
母本（唯一真相源）
  AI协作规划库/1-规则_Rules/个人规则_user_rules.md      ← 通用规则母本
  AI协作规划库/2-技能_Skills/*                          ← 5 个 skill 母本
        │ 单向向下同步
        ├──→ 知识库级  Coding/.trae/            打开 Coding 文件夹时生效
        └──→ 项目级    {{项目名}}/.trae/        打开本项目为根时生效
```

**铁律**：只改母本，再往下同步。**不要在项目副本里单点改**——同一份通用规则会有 2 处、skill 会有 3 处，谁改谁漂。

**为什么每个项目一份**：Trae 只读「工作区根」下的 `.trae/`，父目录的那份不会自动继承（已实测）。所以隔离性靠复制，不靠继承。

### 2.3 新项目启动清单（复制型）

1. 建项目文件夹 `{{项目名}}/`，建骨架目录：`plan/ dev/ test/ usage/ release/ icons/ screenshots/ inbox/`
2. 复制 `dev/可复制项目指南.md` → 全局替换 §6 占位符
3. 复制 `.trae/rules/general_rules.md`（改开头说明块）+ 新写 `.trae/rules/project_rules.md`
4. 整目录复制 `.trae/skills/`（5 个）
5. 写最小可用 `README.md` + 复制 `.gitignore`
6. `git init` + 连远端（**未经确认不提交**）
7. 若用多根工作区：在 `Coding.code-workspace` 的 `folders` 里加一行 `, { "path": "{{项目名}}" }`
8. 另开窗口打开新项目，确认 **Rules 面板 2 条、Skill 面板 5 个**（缺了就是 .trae 没放对位置）

> 以上第 2–5 步都是纯复制，可让 AI 一条命令做完，不必手点。

## 3. 全流程 SOP（六阶段 + 两条贯穿线）

每阶段格式：**触发 → 产物 → 关键规则 → 完成判据(DoD)**。

### 阶段 0｜启动
- **触发**：接到新任务/新项目。
- **产物**：读 `README.md`（没有就先建最小可用版）；在 `session_log.md` 起一条会话条目。
- **规则**：先把需求改写成 3 件事——**用户目标 / 输入输出 / 成功标准**；关键信息缺失只问 1–3 个最关键问题，其余合理假设并写明。
- **DoD**：目标、约束、成功标准一句话说得清。

### 阶段 1｜需求（RPD）
- **产物**：`plan/RPD_需求文档.md`。
- **骨架**：产品定位 / 目标用户 / 功能总览表(含 P0·P1) / 详细功能需求 / UI-UX 原则 / 技术方案 / **分阶段规划(勾选项)** / 成功标准 / 风险与应对。
- **DoD**：每条需求可判定「做没做完」；用户确认后再动代码。

### 阶段 2｜开发
- **规则**：复用现有技术栈；保持简单可读，必要时才抽象；**旧代码不动，新功能进新模块**（如 `modules/`）。
- **产物**：可运行代码 + 关键变更点说明。
- **DoD**：本地加载可跑（扩展类见 `usage/Running.md` 的开发者模式加载法）。

### 阶段 3｜测试
- **产物**：`test/{{功能}}测试清单.md`，逐条勾选。
- **必覆盖的边界**（本项目踩过的坑，务必抄）：输入框内不误触发快捷键、合成事件 `isTrusted=false` 不触发、`Ctrl/Alt/Meta` 组合键不误触、刷新后持久化保持、多功能协同不互相打断。
- **DoD**：清单全绿或已记录已知问题。

### 阶段 4｜版本归档
- **规则**：版本号 `v主.次.补`；大版本完成 `git tag` + release zip。
- **产物**：更新 `version_plan.md`（新增版本条目 + 时间线）与 `plan_github_versioning.md`（**归档表必须回填一行**：Tag/Commit/日期/说明）。
- **DoD**：tag、归档表、version_plan 三处一致。

### 阶段 5｜上架/交付
- **产物**：`release/{{name}}-v{{ver}}.zip` + 各商店 `plan_*_store.md`。
- **规则**：见 §5.7 平台事实表；**文案以代码为准**（§8）。
- **DoD**：包干净（只含运行文件）、文案与代码一致、素材尺寸符合该商店。

### 贯穿线 A｜会话记录
每完成一个重要阶段，往 `session_log.md` 追加固定 6 段摘要（见 §5 模板）。

### 贯穿线 B｜会话交接
长任务/换会话前，产出 `session_handoff_*.md`（见 §5 模板），可整段复制给新会话。

## 4. 版本与 Git 规范

| 版本号 | 含义 |
|---|---|
| `v0.x.0` | 新增一个核心功能模块 |
| `v0.x.y` | 小修复/补丁 |
| `v1.0.0` | 核心齐备、体验稳定、可正式发布 |

- **提交规范**：`feat:` 新功能 / `fix:` 修复 / `refactor:` 重构 / `docs:` 文档 / `chore:` 杂项。
- **分支**：`main`（只接已验收）+ `feature/*`；并行多功能时才引 `dev`。
- **入库**：源码 / manifest / README / Running / session_log / RPD。
- **不入库**：运行时调试日志（如 `*-debug-*.json`）、`日志/`、打包 zip、`.pem` 私钥。
- **打包命令模板**（Python 跨平台，正斜杠路径，只装运行文件）：
```powershell
python -c "import zipfile; files=['manifest.json','{{入口代码}}','{{样式}}','README.md','icons/icon-16.png','icons/icon-48.png','icons/icon-128.png']; z=zipfile.ZipFile('release/{{name}}-v{{ver}}.zip','w',zipfile.ZIP_DEFLATED); [z.write(f,f) for f in files]; z.close()"
```

## 7. 提示词包（新会话直接粘贴）

**① 项目启动 / 需求固化**
```
你是资深产品经理+工程师，我的用户是零基础。先读本项目 README 与 dev/可复制项目指南.md。
把我的需求改写成 3 件事：用户目标 / 输入输出 / 成功标准；只问我 1–3 个最关键问题，其余合理假设并写明。
确认后按指南 §3 阶段 1 产出 plan/RPD_需求文档.md。未经我确认不写代码。
```

**② 阶段开发**
```
按 RPD 的分阶段规划实现「{{阶段}}」。规则：复用现有技术栈、保持简单、旧代码不动新功能进新模块。
交付：可运行代码 + 关键变更点说明 + 该功能的 test/ 验收清单（含输入框不触发、isTrusted、组合键、刷新持久化等边界）。
```

**③ 文案与事实校验（防「凭记忆写错」）**
```
在写任何商店 Listing / 快捷键说明前，先 grep 代码核对事实，再据实产出文案：
- 快捷键：看入口脚本的键盘处理函数（本项目为 content.js 的 handleAllKeyboard）
- 权限：manifest.json 的 permissions
- 生效域名：manifest.json 的 matches
以代码结果为准，覆盖记忆与旧文案。
```

**④ 打包上架**
```
按指南 §4 打包命令生成 release/{{name}}-v{{ver}}.zip（只含运行文件，正斜杠路径）。
按 §5.7 平台事实表核对目标商店的上传物与图片尺寸。注册账户/点提交由我手动，你不要代做。
```

**⑤ 会话交接**
```
产出 session_handoff_{{任务}}.md：版本/优先级、本会话已完成、下一步(谁做·手动还是自动)、关键文件路径表、红线提醒。要能整段复制给新会话。
```

## 8. 红线清单（每次都要守）

- **版本号必须递增**，且高于目标商店上次提交，否则被拒。
- **文案以代码为准**：快捷键/权限/域名先 grep 再写（本项目曾因凭记忆写错快捷键 `T` 翻车）。
- **`.pem` 私钥 / 密钥 / token / 隐私一律不入库、不写进 session_log / handoff。**
- **未经用户明确确认**：不 `git commit`、不注册账户、不代替用户提交审核。
- **360 上传的是「含 crx 的 ZIP」**，且图片尺寸与 Edge/Chrome 完全不同，需另裁。
- 每次 `git tag` 后**回填** `plan_github_versioning.md` 归档表。
